FULL SYSTEM VIEW

Two flows meet at the index

The crawler prepares pages before anyone searches. A query reads the prepared index and returns a ranked page of results.

01 / FIRST VERSION

Three saved pages → PostgreSQL scan → simple overlap score → Nina's browser

Working search for a tiny collection. The pages were loaded by hand.
02 / CRAWL BEFORE QUERY

Known links + sitemaps → URL frontier → robots check + paced fetch → extract + noindex + deduplicate

Discovery, fetch, and indexing decisions are separate. A discovered URL may never become a result.
03 / BUILD THE INDEX

Canonical document → OpenSearch analyzer → term postings → searchable index

Use the canonical document ID for updates and deletions. The index is derived from crawler records.
04 / ANSWER THE QUERY

Nina → Search API → analyzed query + postings → BM25 + title weight → source checks → snippet + result

Shards later split this work across nodes; they do not change the user's query path.

Trace Nina's query: grow basil indoors → [grow, basil, indoors] → candidate IDs d1, d2, d3 → scored top hits → title + URL + snippet Example documents and URLs are invented for teaching. Scores and order beyond the strongest match depend on the indexed corpus and ranking choices.

BUILD IT IN STAGES

Add the next part when the old route breaks

The query never crawls the live web while Nina waits.

01 / WORKING

Table scan

Save three pages by hand in PostgreSQL. Scan them for query words and show a title, URL, and preview.

02 / FIND AND RANK

Crawler + index

Discover and fetch permitted pages, extract one representative document, then use OpenSearch postings and BM25 to answer quickly.

03 / KEEP GROWING

Recrawl + shards

Update or delete stale results, let workers share a durable frontier, and split the search index only when one node is no longer enough.

A URL has several different milestones

Discovery DISCOVERED → DUE → LEASED → FETCHED or RETRY_AT.

Index decision Indexable → canonical document → indexed, or excluded.

Query Candidate → scored hit → shown result.

A 200 response does not guarantee indexing. Indexing does not guarantee that a page matches a particular query or appears in its top results.
The three documents and exact postings
d1 · /basilTitle: “Grow basil indoors.” Body: “Basil needs bright light indoors. Grow it near a window.”
d2 · /indoor-herbsTitle: “Indoor herb guide.” Body: “Basil indoors needs bright light.”
d3 · /basil-pruningTitle: “Pruning basil outside.” Body: “Grow basil outdoors and trim its stems.”

First table scan: Count distinct query words across title and body; break ties by title matches. d1 scores 3 words, d3 scores 2 with a title match, and d2 scores 2 without one. The first version shows d1, d3, d2. This is a teaching rule, not BM25.

After lowercasing and splitting terms: basil → d1,d2,d3; indoors → d1,d2; grow → d1,d3. These are simplified posting lists across title and body. A real index keeps field-specific postings and more information such as term frequency and positions.

Candidate policy: OR across the three terms retrieves d1,d2,d3. d1 matches all three; the actual BM25 scores depend on collection statistics and field settings. The page does not claim fixed scores for this example.

Exact search request

The app can ask OpenSearch for 50 text candidates with a modest title weight, apply bounded source checks, then show ten results. This example uses the default best_fields form of multi_match and a body highlight.

POST /pages/_search
{
  "size": 50,
  "query": {
    "multi_match": {
      "query": "grow basil indoors",
      "fields": ["title^2", "body"],
      "operator": "or"
    }
  },
  "highlight": {"fields": {"body": {}}}
}

Response handling: Read _id, _score, canonical URL, title, and optional highlight fragment for each candidate. Apply the stated source checks, then return ten. Escape untrusted page text before rendering. Return an empty state if there are no hits; surface timeout or shard failure instead of silently pretending the whole index was searched.

What the text score misses

Language: This worked search is in English, so its serving policy keeps English results. Multilingual search would need language-aware matching and evaluation.

Links: The crawler can count distinct external hosts that link to a page. A small capped tie-breaker may help near-equal text matches, but raw link count is easy to manipulate and cannot prove a claim is true.

Abuse: Keep a reviewed exclusion policy for confirmed malicious or deceptive results. Keyword stuffing and link spam are examples of why a strong text score is insufficient.

Freshness: Re-crawl to keep documents current. Prefer recent documents only when the query calls for recent information; basil care does not become better solely because a page is newer.

Exact crawler records and decisions

frontier: normalized_url, host, discovered_from, state, next_fetch_at, lease_until, attempts, last_status. Unique normalized_url prevents repeated queue rows.

documents: doc_id, fetched_url, canonical_url, title, body, language, content_hash, fetched_at, indexable, extraction_version. The canonical document ID is also the OpenSearch _id.

HTTP path: GET /robots.txt → check current URL → wait for host slot → GET page → record status and final URL → parse HTML and links → apply noindex and duplicate grouping → upsert or delete index entry.

robots.txt: It controls fetch access. A page-level noindex must be fetched to be seen. Neither is a password system. A sitemap is a URL suggestion, not a promise to crawl or index.

Redirects and untrusted URLs: Validate each new destination, block internal networks and metadata endpoints, cap redirects, response size, and time. A crawler must not turn public links into access to its own private network.

How two crawl workers avoid taking the same job

In one PostgreSQL transaction, claim one due frontier row and give it a lease. A second worker skips that locked row. The separate host scheduler still decides when the URL may be fetched.

WITH picked AS (
  SELECT normalized_url FROM frontier
  WHERE (state IN ('DISCOVERED', 'DUE', 'RETRY_AT')
         AND next_fetch_at <= now())
     OR (state = 'LEASED' AND lease_until < now())
  ORDER BY next_fetch_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
UPDATE frontier AS f
SET state = 'LEASED', lease_until = now() + interval '2 minutes'
FROM picked
WHERE f.normalized_url = picked.normalized_url
RETURNING f.normalized_url;

After the claim: Commit, reserve a host slot, fetch, and report the outcome. If no host slot is available, release or reschedule the job. If the worker dies, its lease expires and another worker may try. The two-minute lease is a teaching choice; a slow fetch can outlive it, so updates must be safe to repeat.

Ranking limits and failure drill

No result: Check whether the URL was discovered, allowed, fetched, indexable, canonicalized, indexed, and finally matched. Each stage has a separate reason for absence.

Wrong result first: Inspect analyzer tokens and OpenSearch score explanation. Evaluate title weight on a fixed judged set; do not assume a high text score means the page is trustworthy.

Dead result: Recrawl. Remove a confirmed 404/410 or noindex page from the index; retry a transient timeout or 5xx rather than deleting immediately.

Stale result after update: Compare document and index versions, then wait for index refresh or reconcile a failed update. Search is near real time, not an instant view of every crawl write.

Slow query: Inspect candidate count, query time, highlight cost, and shard load. More shards consume resources and should follow measurement.

Key terms

Frontier The durable list of URLs waiting to be fetched or revisited.

Crawl Fetch a page from its host, subject to crawl rules and rate limits.

Index Analyze a chosen page and store searchable terms and document data.

Canonical URL The representative URL for a group of duplicate or near-duplicate pages.

Analyzer The rules that turn text into searchable terms.

Inverted index A map from term to documents containing that term.

Posting A term's entry for one document, possibly including frequency and positions.

BM25 A text relevance score based on term frequency, rarity, and field length.

Shard A portion of the index that can live on one search node; a replica is another copy.

Sources and scope

This is an illustrative small public-web search engine using PostgreSQL for URL and document records and OpenSearch for the search index. Example URLs, IDs, worker states, and ranking weights are teaching choices. It is not a description of Google's private ranking system. Image/video search, ads, semantic retrieval, personal results, and large-scale spam defense require separate designs.
