FULL SYSTEM VIEW

The first route and the grown route

Both routes use the same private file record, checking step, and share link.

01 / FIRST UPLOAD

Maya browser → app API receives bytes → private S3 staging → scan → published object + READY row

Simple to build. The app server carries every uploaded byte.
02 / DIRECT UPLOAD

Maya browser → app issues signed POST → S3 staging → version-pinned check + scan → same published object

The app authorizes and finalizes; S3 receives the bytes. A staging object is never the shared file.
03 / SHARED DOWNLOAD

Leo → app share-token check → app stream or short-lived signed GET → private S3 bytes

The share link is stable and revocable for new requests. A signed GET already issued lasts until its own expiry.

Trace this file: report.pdf, 4 MiB → file_id=f-41 → staging key=staging/u-41 → published key=files/f-41 → /s/<random-token> IDs, paths, and endpoints are a teaching design. The bucket stays private.

BUILD IT IN STAGES

Add a component when a failure demands it

The public link only appears after the file is checked and published.

01 / WORKING

App carries bytes

Authenticate Maya, stream the upload through one app server into private S3, record a file row, check the content, then create a share token.

02 / LESS APP TRAFFIC

Browser uploads to S3

Give Maya a short-lived signed POST with one staging key and a size cap. Record the exact S3 version, check it, then copy it to a server-owned published key.

03 / LARGER FILES

Parts and cleanup

Use multipart upload when one request is impractical. Resume missing parts, complete once, abort abandoned uploads, and use multipart copy above S3's single-copy limit.

The file and the link have separate states

File PENDING → STAGED → CHECKING → READY (or REJECTED).

Share link ACTIVE → EXPIRED or REVOKED.

A successful S3 upload is not the same as a READY file. A READY file is not automatically shared.
Exact records and API calls

files: id, owner_id, original_name, expected_size, staged_key, staged_version, final_key, status, created_at. A unique final key is generated by the server.

shares: id, file_id, token_hash, expires_at, revoked_at. The raw random token is returned once in the link; the database stores its hash.

First route: POST /files with file bytes → PENDING row → private staging object → checks → final object → READY.

Direct route: POST /uploads with name, size, and base64 SHA-256 → upload_id + S3 POST fields. Browser POSTs the fields and file to S3; S3 returns x-amz-version-id. POST /uploads/{id}/complete with that version returns CHECKING. A worker checks that exact version, scans, copies, then marks READY.

Sharing: POST /files/{id}/shares returns /s/{token}. GET /s/{token} checks the share and READY file on every new request, then streams bytes or redirects to a short-lived signed GET.

Why there are two storage keys

Staging key: a short-lived upload permission can be reused before it expires. In a versioned staging bucket, each accepted write gets an S3 version ID. The server scans and copies one specified version.

Published key: only the app's server role can write here. It is unique to this file and is never handed to the browser for upload. The share link points to the file record, which points to this key.

Order: copy the checked version first; mark the database row READY only after the copy succeeds. If the database update fails, clean up the unused published object later.

Failure drill

Browser stops mid-upload: file row stays PENDING or STAGED. The user can retry; a cleanup job removes stale rows and staging versions.

S3 accepted bytes, browser missed the reply: reconcile using the upload session and exact version before starting another attempt. Never infer success from a progress bar.

Scan fails: mark REJECTED, keep the share endpoint closed, and delete or quarantine according to policy.

Copy succeeds, DB update fails: a published object exists without a READY row. Reconcile or delete it; do not issue a share link early.

Share is revoked: new /s/{token} requests fail. A signed GET already handed out remains usable until it expires; use app streaming if every request needs an immediate policy check.

Security and browser details

Type: the filename and browser Content-Type are hints, not proof. Allow only needed types, inspect bytes, scan risky content, and keep untrusted uploads away from the site's own origin.

Upload policy: sign an exact staging key, a content-length-range, and the checksum field. Keep the bucket private. S3 CORS must allow the app origin and POST, and expose x-amz-version-id for the direct route.

Download: use Content-Disposition: attachment with a safe filename for this PDF flow. An anyone-with-link URL is a bearer secret; keep it out of logs and third-party page requests, and use a no-referrer policy on the share page.

Limits: cap upload size and rate per account, limit share redemption rate, and set lifecycle cleanup for incomplete multipart uploads and old staging versions.

Key terms

Object key The private storage name for bytes in S3; it is not the share URL.

Signed POST A temporary S3 form policy for uploading to one allowed staging key.

Version ID S3's identity for one write to a key in a versioned bucket.

Checksum A value used to detect changed bytes during transfer. It does not declare content safe.

Share token A random secret in the stable app link, checked against the share record.

Signed GET A temporary storage URL created only after the app accepts a share request.

Multipart upload S3's way to upload a large object as separately retriable parts.

Sources and scope

This is a teaching design for a 4 MiB PDF in a private, versioned S3 bucket with PostgreSQL metadata. The file IDs, API paths, state names, and share rules are chosen here; they do not describe a particular service's internals. The later multipart path is an alternative for larger files.
