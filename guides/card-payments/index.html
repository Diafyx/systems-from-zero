Where the tools fit

The store builds the order flow. The provider and banks handle the card route.

01

Checkout

A provider-controlled card form, such as Stripe Payment Element, collects card details. The store API creates the order and payment request.

02

Payment state

A verified webhook updates the order in PostgreSQL. Idempotency keys and safe event handling help with retries.

03

Events, if needed

As the store grows, an outbox can send a paid-order event to Kafka. Workers use it for fulfillment, email, or analytics. The issuer still decides whether to approve the card.

Key terms

Issuer The shopper's card bank; it approves or declines.

Acquirer The store's bank or acquiring partner.

Card network Routes messages between the two sides.

3-D Secure An extra check of the shopper's identity when needed.

Authorization The decision to approve or decline; an approval usually places a hold.

Capture, clearing, settlement Submit the approved charge, exchange transaction records, then move funds.

Webhook A server-to-server update from the provider.

Sources and scope

This is a teaching model of a typical online card purchase. Routes and timing vary by provider and region. The software choices above are examples.

  • Visa: payment lifecycle
  • Stripe: Payment Element
  • Stripe: webhooks
  • Stripe: idempotent requests
