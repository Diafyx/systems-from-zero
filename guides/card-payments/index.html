FULL SYSTEM VIEW

Three paths, one payment

The request, the store record, and the money move on different paths.

01 / CARD REQUEST

Shopper → secure checkout → provider → acquirer → network → issuer

Approval or decline returns through the provider. 3-D Secure may happen during confirmation.
02 / STORE STATE

Provider event → verified webhook → order database → fulfillment

Start with a database worker. Add an outbox and Kafka only when more services need the event.
03 / MONEY

Authorization → capture → clearing → settlement → provider balance → payout

Reconcile provider transactions and fees with the bank deposit. Refunds and disputes can change the balance later.

Trace the $42 order: ord_1042 → pi_example → ch_example → txn_example → po_example Example IDs: order, payment, charge, balance transaction, payout. One payout can include many transactions.

IMPLEMENTATION BLUEPRINT

Build it without losing track

These are the records and rules behind the diagram.

01 / BASE

Start with the small system

Server-priced order, provider checkout, a stored payment ID, verified webhooks, and a database-backed fulfillment job. This is enough for a clear first version.

02 / RELIABILITY

Make retries safe

Use idempotency keys for provider writes, unique provider event IDs, monotonic order states, and idempotent fulfillment. Timeouts are unknown until checked.

03 / GROWTH

Add tools for a reason

Use an outbox when database changes must reliably produce events. Kafka becomes useful when multiple services need the stream. Add reconciliation as volume grows.

Keep two kinds of state

Store order awaiting_payment → authorized → paid → fulfilled

Provider payment requires_payment_method → requires_action if needed → requires_capture → succeeded

A decline returns the payment to requires_payment_method and leaves the order unpaid. Refunds and disputes have separate records; they do not erase the original payment.
Webhook processing sequence
  1. Verify the signature against the unmodified request body.
  2. Find the order through the provider payment ID; check amount and currency.
  3. Record the provider event ID with a unique constraint.
  4. In one database transaction, mark the order paid once and write a fulfillment job or outbox event.
  5. Return a success response after durable acceptance. Let the worker handle shipping or email.

If events arrive out of order, read the provider's current payment state and apply only a valid forward transition. Never let an old event reverse a paid order.

Records to keep
ordersorder_id, amount, currency, payment_state, fulfillment_state
payment_attemptsorder_id, provider_intent_id, provider_status, authorized_amount, captured_amount
provider_eventsevent_id (unique), event_type, provider_object_id, received_at
outboxevent_id (unique), aggregate_id, event_type, payload, published_at
refunds / disputestheir own IDs, amounts, statuses, and link to the original payment

These are teaching fields, not a complete production schema. Store credentials and secrets separately; never put raw card details here.

Failures to test

Price changed: server recomputes the amount before payment creation.

Card declined: order stays unpaid; shopper can try again.

3-D Secure abandoned: order stays pending until provider state resolves.

API timed out: retrieve or retry the same operation with its idempotency key.

Webhook repeated or reordered: only one paid transition and one fulfillment.

Capture expired: do not fulfill; ask for a new payment attempt.

Refund failed or dispute opened: track a separate case and adjust finance records.

Key terms

Issuer The shopper's card bank; it approves or declines.

Acquirer The store's bank or acquiring partner.

Card network Routes messages between the two sides.

3-D Secure An identity check when required.

Authorization Approval to charge; usually a hold, not merchant funds.

Capture Submission of an approved charge.

Clearing and settlement Exchange transaction records, then move funds between institutions.

Payout Provider sends available balance to the merchant bank.

Webhook A server-to-server provider update.

Outbox A durable record of an event to publish after a database change.

Sources and scope

This is a worked example of a Stripe PaymentIntent with manual capture for one online card order. It exposes the states for learning. Stripe recommends Checkout Sessions for most real integrations. Downstream bank message formats and timing differ by network, provider, and region; the handoffs here are conceptual, not copies of bank wire messages.
