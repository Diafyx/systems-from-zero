FULL SYSTEM VIEW

Money, stock, and parcel move on different paths

They meet at the order record. Each path has its own status and evidence.

01 / FIRST STORE

Asha → store app + Stripe charge → staff pick and pack → local driver → manual delivery report

Works for a few orders. Physical stock and delivery updates rely on people.
02 / SAFE CHECKOUT

Checkout key → PostgreSQL order + stock hold → Stripe authorization → PLACED order + outbox → SQS

One stock hold and one payment attempt belong to one order. Authorization is not capture.
03 / WAREHOUSE

SQS worker → W1 pick task → barcode scan → packed box → Shippo label → Stripe capture

A label and tracking number can exist while the box is still at W1.
04 / DELIVERY

W1 dock handoff → UPS scans → last-mile driver → Shippo tracking update → Asha's order timeline

Carrier milestones are scan reports. A disputed or returned parcel gets a separate case.

Trace this pair: RUN-BLU-09 → order o-41 → W1 stock hold → pick p-41 → shipment s-41 + tracking number → carrier DELIVERED event IDs, prices, state names, and endpoints are a teaching design. The first and upgraded routes replay the same hypothetical purchase; they are not two real charges.

BUILD IT IN STAGES

The next part solves a specific failure

Do not make Asha wait for a parcel to travel before the site confirms her order.

01 / WORKING

One room, one driver

Charge at checkout, save an order, have staff pack it, and record delivery by hand. Missing stock and manual updates are visible weaknesses.

02 / SAFE AND REPEATABLE

Reserve, authorize, fulfill

Give checkout one retry key, reserve stock atomically, authorize the card, and send a durable warehouse task from the order transaction.

03 / MANY PARCELS

Scan, label, track

Scan the picked SKU, buy a carrier label, capture before handoff, record actual carrier scans, and reconcile failed or delayed updates.

Four clocks for one order

Order PENDING_PAYMENT → PLACED → HANDED_OFF → DELIVERED (or EXCEPTION).

Payment requires_capture → succeeded, or canceled before capture.

Stock at W1 on_hand 3, reserved 0 → 3,1 → 2,0 after handoff.

Parcel PICKING → PACKED → LABEL_CREATED → HANDED_OFF → IN_TRANSIT → DELIVERED.

A PLACED order is not paid in the manual-capture route. A label is not carrier possession. A delivered scan can still be disputed.
Exact records and API calls

orders: id, checkout_key (unique), customer_id, sku, quantity, amount_cents=8800, address_snapshot, warehouse_id, order_state, payment_state, payment_intent_id. The accepted amount and address are snapshots; later catalog edits do not rewrite this order.

stock: warehouse_id + sku primary key, on_hand, reserved. reservations: order_id (unique), warehouse_id, sku, quantity, expires_at, state. HELD is temporary; COMMITTED lasts through fulfillment; RELEASED or CONSUMED closes the claim.

fulfillments: task_id, order_id (unique for this one-parcel order), warehouse_id, bin, picked_sku, picked_at, packed_at. shipments: shipment_id, order_id, Shippo transaction ID, carrier, tracking_number, state, handoff_at.

events: outbox(event_id, order_id, type, sent_at) and tracking_events(shipment_id, provider_event_key, carrier_status, carrier_event_at, received_at). Deduplicate callbacks and keep original carrier times.

Checkout: POST /checkouts with checkout_key=c-41 → o-41. Stripe create/confirm PaymentIntent for 8800 USD cents with manual capture and a stable idempotency key. The app treats requires_capture as AUTHORIZED.

Shipping: after pick and pack, POST /shipments to Shippo with sender, recipient, and parcel measurements; choose a UPS rate; POST /transactions with that rate to buy the label. Store transaction ID only when its status is SUCCESS, plus the tracking number. Capture the linked PaymentIntent before dock release. Shippo track_updated calls the app with later carrier status.

The stock transaction that stops two buyers taking one pair

For an existing W1 stock row, run this UPDATE inside a PostgreSQL transaction. If it returns one row, insert reservation(o-41,W1,RUN-BLU-09,1) and commit. If it returns no row, roll back and report out of stock.

UPDATE stock
SET reserved = reserved + 1
WHERE warehouse_id = 'W1'
  AND sku = 'RUN-BLU-09'
  AND on_hand - reserved >= 1
RETURNING on_hand, reserved;

Cancel before handoff: mark the reservation RELEASED and decrement reserved once. Handoff: mark it CONSUMED and decrement both on_hand and reserved once. Guard each transition by its prior state so retries do not move stock twice.

What happens if a response goes missing

Checkout response lost: Asha retries c-41. The store returns o-41; it does not create a second order.

Stripe reply lost: Read pi-41 and its status before another request. Reuse the same Stripe idempotency key for the same operation and parameters.

Authorization succeeded, order commit failed: Reconcile o-41 and pi-41. If its stock hold is still valid, retry the guarded PLACED transaction; otherwise cancel the uncaptured PaymentIntent and release any remaining hold.

Order commits but SQS send fails: The outbox row remains unsent. The relay retries; the worker uses o-41 to avoid a second pick task.

Label reply lost: Reconcile the Shippo transaction or search by stored attempt details before buying another label. A second purchase can cost money and create another tracking number.

Capture fails: Keep the box at W1. Do not hand it to UPS; resolve payment or cancel. An expired authorization cannot simply be captured later.

Tracking callback missing: Poll the carrier/Shippo tracking record and compare event history. Do not move the order backward because an older event arrived late.

Where the physical handoffs happen

Reserved: A database claim on a pair. The pair may still be on the shelf.

Picked: Staff found and scanned a matching physical pair. It can still be damaged or packed incorrectly.

Label created: Shippo purchased postage and returned a tracking number. UPS may not yet have the box.

Handed off: W1 gave the parcel to a UPS pickup driver and recorded dock evidence. The first carrier scan may arrive after this.

Delivered: The carrier reported the delivery milestone. Keep support and proof-of-delivery paths for disputes.

Card, address, and webhook boundaries

Card details: Use Stripe's Payment Element or equivalent client-side collection. The store app holds the PaymentIntent ID and status, not Asha's raw card number. Keep Stripe secret keys on the server; do not log the client secret.

Address: Store it with restricted access for fulfillment and support. The SQS event contains o-41 and W1, not Asha's full address; the authorized warehouse worker looks up only the fields it needs.

Tracking callback: Configure one of Shippo's webhook protection methods, such as HMAC where enabled. Verify the sender and match the tracking number to a shipment before accepting any status. Keep the original payload for investigation.

What to measure and reconcile

Checkout: duplicate-key returns, failed stock holds, authorizations stuck near expiry, payment failures, and PENDING_PAYMENT age.

Warehouse: outbox age, SQS retry count, pick exceptions, wrong-SKU scans, packed-but-uncaptured orders, and labels without handoff.

Carrier: handoffs without first scans, delivery estimate changes, exceptions, callbacks delayed past a threshold, and DELIVERED disputes.

Daily reconciliation: compare order state with reservation, Stripe PaymentIntent, fulfillment task, label transaction, and carrier history. Put mismatches into a human review queue with exact IDs.

Key terms

SKU The store's exact product variant, including size and color.

Reservation A temporary claim that reduces sellable stock without removing the item from the building.

Authorization A card hold that may later be captured or canceled; it has a time limit.

Capture The payment step that takes funds after authorization.

WMS Warehouse management software that tracks bins, picks, and packing work.

Outbox An event row committed with the order, then sent to a queue by a relay.

Shipping label Carrier routing and tracking information attached to a parcel, created before pickup.

Tracking event A carrier-reported milestone with its own event time.

Sources and scope

This is a teaching design for one domestic shoe order, one parcel, a card payment, and a store-owned warehouse. Stripe, Shippo, UPS, PostgreSQL, and SQS are concrete examples. The IDs, order states, shipping policy, and stock schema are chosen here; they do not describe any retailer's private system. Tax calculation, fraud review, split shipments, international customs, and warehouse purchasing need their own flows. The card-payment guide explains bank authorization and capture in more depth.
