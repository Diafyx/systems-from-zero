FULL SYSTEM VIEW

One message, three paths

The database is the shared record. Live sockets and push tell devices that record changed.

01 / ACCEPT AND SAVE

Asha device → WSS gateway → auth + membership → PostgreSQL commit → sender ACK

The server ACK means saved. A socket send alone does not mean accepted.
02 / DELIVER WHILE ONLINE

Saved message → Ravi's socket → device store → delivery ACK → optional read event

Delivered and read are application states reported by Ravi's device.
03 / RECOVER WHEN OFFLINE

Saved message → optional push hint → reconnect → fetch after cursor → dedupe + ACK

Push can be delayed or lost. The catch-up query closes the gap.

Trace one message: client_message_id=asha-73 → server message_id=m-918, conversation=c-42, seq=18 → Ravi device ACK at seq=18 These are teaching IDs and a proposed application protocol, not values from a real chat service.

BUILD IT IN STAGES

The smallest useful system, then the hard parts

Each stage fixes a failure exposed by the previous one.

01 / WORKING

One app server

Use WSS for live messages and PostgreSQL for conversations, members, and messages. Save before replying to Asha. Route to Ravi if connected.

02 / RELIABLE

Retries and catch-up

Add a stable client message ID, uniqueness rule, per-conversation sequence, device cursor, delivery ACK, and reconnect sync. Add push as a wake hint.

03 / GROWING

Many gateways

Track which gateway holds each live device. Add a database outbox and Kafka when workers or gateways need committed events. Consumers still dedupe and clients still sync.

The three states are separate

Sent PostgreSQL committed; Asha has the server ACK.

Delivered at least one Ravi device saved the message and acknowledged it.

Read a Ravi device reported that the conversation reached this message.

These are this example's product rules. “Read” reports an app event, not proof a person understood the text. Multi-device products may choose different receipt rules.
Records and constraints

conversations: id, next_seq. Lock its row while assigning the next message number.

members: conversation_id, user_id, membership state. Check membership again in the save transaction if removal can race a send.

messages: message_id, conversation_id, seq, sender_id, client_message_id, body, created_at. Enforce unique (conversation_id, seq) and unique (sender_id, client_message_id). Keep IDs and sequence values non-null.

device_cursors: device_id, conversation_id, highest contiguous seq saved. Store delivery and read receipts separately if the product displays them.

outbox, at scale: event_id, conversation_id, message_id, seq. Insert with the message in the same transaction; publish after commit.

Exact save and catch-up algorithms

Send transaction:

  1. Read the authenticated user from the socket session. Validate the payload before opening a database transaction.
  2. Begin a transaction and lock the c-42 conversation row. Confirm that Asha is still a member.
  3. Look up (Asha, asha-73). If it exists, verify the original conversation and body, then return its message ID and sequence after the transaction ends.
  4. If absent, take next_seq as the new sequence, increment next_seq, and insert the message. At scale, insert its outbox event in this same transaction.
  5. Commit. Send Asha the server ACK. Route the committed message to Ravi's connected devices.

Catch-up: Ravi sends his last contiguous saved sequence for c-42. Check membership, query later messages in sequence order with a page limit, and send the page. Ravi saves each unseen message by message_id, advances his cursor only through contiguous sequences, and acknowledges stored messages. Repeat until caught up.

Client ID: use a random unique value in a real app. The short IDs here make the trace easy to read.

Failure drill

ACK lost after commit: Asha retries the same client_message_id; return the existing message_id and seq.

Ravi's socket closes: keep the saved row. Reconnect fetches messages after the device's last contiguous seq.

Push is late or dropped: chat remains in PostgreSQL. A later app open runs the same catch-up query.

Two sends race: one conversation row lock serializes sequence assignment. Render by seq, not client timestamps.

Worker handles an event twice: identify it by event_id or message_id and make the consumer safe to retry.

How delivery works across many gateways

Connection directory: when Ravi's device connects, its gateway records device_id → gateway_id in a shared store such as Redis. Renew a short expiry while the socket is alive. A stale entry only means a live attempt can fail; reconnect sync still repairs the gap.

Committed event: the message transaction also writes an outbox row. A relay publishes that row to Kafka with conversation_id as key, so one conversation's events land in one partition under a stable partition layout.

Final hop: a worker reads the event, finds Ravi's connected devices, and forwards m-918 to their gateways. Each gateway writes to its local sockets. Devices dedupe by message_id and ACK after saving.

Ordering: Kafka orders events inside a partition. The chat UI still orders by the PostgreSQL sequence; it must tolerate duplicate or late event delivery.

Security and optional features

Transport: WSS protects the device-to-server connection. Authorize each socket and each conversation action. Limit message size and send rate.

End-to-end encryption: requires client key management and encrypted message bodies. WSS alone is not end-to-end encryption; a server holding plaintext can read it.

Attachments: store file bytes in object storage and send a reference in the message after upload and access checks. That is a separate flow.

Deletion and retention: define how clients advance past removed sequence numbers, for example with a tombstone. Do not silently skip a missing message.

Key terms

WSS WebSocket over TLS: a live two-way connection.

Server ACK An application reply after the database commit.

Client message ID A stable ID made by the sending device and reused on retry.

Sequence The server's order for messages in one conversation.

Cursor The last contiguous message sequence saved by one device.

Delivery ACK A recipient device's report that it saved a message.

Outbox A database row recording an event to publish after the same transaction commits.

Sources and scope

This is a buildable teaching design for a one-to-one chat. The IDs, protocol messages, receipt meanings, and tables are defined for this example; they do not describe any company's private implementation. WebSocket, PostgreSQL, FCM, Debezium, and Kafka documentation support the stated behavior of those tools. Push and Kafka are optional additions.
