FULL SYSTEM VIEW

One seat row joins four separate paths

The map helps people choose. The database claim decides who may pay. Payment, ticket issue, and entry each have their own state.

01 / FIRST VERSION

Buyer → seat map → read AVAILABLE → insert booking

Fine for one buyer. Two workers can both read AVAILABLE and both confirm.
02 / OWNERSHIP

Nina + Leo → Booking API → PostgreSQL guarded UPDATE → one HELD seat

The winner gets H1 with a server deadline. The loser gets zero rows.
03 / PAYMENT AND TICKET

H1 → Stripe authorize → FINALIZING → Stripe capture → SOLD + outbox → T1

FINALIZING keeps the seat blocked while the external capture result is uncertain.
04 / ENTRY AND RUSH

QR token → online gate check → VALID to USED · Waiting Room → controlled sale traffic

A copied QR loses the second race. Rush controls protect the app, not seat ownership.

Trace this seat: E7/A-12 → H1 → O1 → Stripe P1 → SOLD → ticket T1 → USED IDs, prices, state names, and endpoints are a teaching design. The first and safe versions replay one hypothetical sale; they are not two real bookings or charges.

Three state machines for A-12

Seat AVAILABLE → HELD(H1) → FINALIZING(O1) → SOLD(O1). An expired HELD can return to AVAILABLE or be claimed by H2.

Payment requires_payment_method → requires_action if needed → requires_capture → succeeded; failure or cancellation takes another branch.

Ticket absent → VALID(T1) → USED. Refund or cancellation can move VALID to REVOKED under an explicit policy.

Payment status and seat status are distinct. A successful capture is followed by a recoverable SOLD commit; it is never assumed to be atomic with Stripe.
Exact records and request contracts

event_seats: event_id + seat_id primary key, state, hold_id, hold_expires_at, order_id, price_cents. One row exists before sale. Only server-side code changes its state.

orders: id, checkout_key unique, buyer_id, event_id, seat_id, accepted_amount_cents=5000, state, payment_intent_id, capture_operation_key. Bind one checkout key to immutable buyer, seat, amount, and hold details.

tickets: id, order_id unique, event_id, seat_id, token_hash unique, status, issued_at, checked_in_at. Keep a unique active ticket per event seat. A token is a random bearer secret, not the visible seat label.

outbox: event_id unique, type, order_id, created_at, sent_at. The worker may see an event twice and must return the existing ticket for O1.

Requests: GET /events/E7/seats is a snapshot. POST /holds claims a seat and returns H1 + deadline or unavailable. POST /checkouts with C1 and H1 returns O1. GET /orders/O1 reports the durable result. POST /gate/check-ins sends token + E7 and returns admitted or rejected.

The exact race and the winning seat claim

Broken timeline: Nina reads AVAILABLE → Leo reads AVAILABLE → Nina inserts B1 → Leo inserts B2. A read followed by a separate insert is not an exclusive claim.

For an existing seat row, run one PostgreSQL UPDATE. Use a server-generated, unguessable H1. One returned row means the caller owns the hold. Zero means unavailable. A second concurrent UPDATE waits and rechecks the row after the first commits.

UPDATE event_seats
SET state = 'HELD',
    hold_id = :hold_id,
    hold_expires_at = clock_timestamp() + interval '5 minutes',
    order_id = NULL
WHERE event_id = :event_id AND seat_id = :seat_id
  AND (state = 'AVAILABLE'
       OR (state = 'HELD' AND hold_expires_at < clock_timestamp()))
RETURNING hold_id, hold_expires_at;

Do not make a separate availability SELECT the acceptance condition. A cached map and a late expiry sweeper cannot decide the winner.

How checkout crosses the payment boundary

Authorize: Create Stripe P1 for 5000 USD cents with manual capture and a stable create idempotency key. Complete card authentication as needed. Continue only when P1 is requires_capture.

Freeze: Before capture, change HELD H1 to FINALIZING O1 with a guarded UPDATE requiring the same hold ID and a live server deadline. Commit this transaction before calling Stripe; do not hold a database lock during a network call. If no row returns, cancel P1 while uncaptured. FINALIZING is never reclaimed by the hold expiry path.

UPDATE event_seats
SET state = 'FINALIZING', order_id = :order_id
WHERE event_id = :event_id AND seat_id = :seat_id
  AND state = 'HELD' AND hold_id = :hold_id
  AND hold_expires_at > clock_timestamp()
RETURNING seat_id;

Capture: Call Stripe capture on P1 with a stable key for O1. If the reply is lost, retrieve P1 and resolve its actual state. Keep the seat FINALIZING while unknown. The site's hold deadline and Stripe's authorization expiry are different clocks.

Commit: On confirmed succeeded, commit SOLD(O1), PAID(O1), and TicketRequested(O1) in one local transaction. If that commit fails, retry it after reconciliation; do not free the seat. If P1 is confirmed canceled or failed, release FINALIZING only with a guarded update matching O1; keep a record of the failed attempt.

How the gate prevents ticket reuse

The QR carries a random token. The online gate API hashes it, matches the event, and performs this update. One returned row means admit. Zero means unknown, revoked, wrong event, or already used; show the precise reason to authorized staff without leaking it to the public scanner response.

UPDATE tickets
SET status = 'USED', checked_in_at = clock_timestamp()
WHERE token_hash = :token_hash
  AND event_id = :event_id
  AND status = 'VALID'
RETURNING ticket_id, seat_id, checked_in_at;

Two online gates racing on T1 cannot both update VALID. Offline scanning requires a separate policy for conflicting scans and is outside this route.

Failure drills to run before a sale

Two buyers: Force concurrent claims for A-12; assert exactly one H1 and one loser. Repeat with one expired HELD row and ensure an old hold cannot finalize.

Checkout retry: Send C1 twice, including after a lost HTTP response. Assert one O1 and one P1. Reuse C1 with a different seat or amount and assert rejection.

Authentication delay: Let H1 expire before P1 reaches requires_capture. Assert no capture and no ticket; cancel the uncaptured intent.

Capture reply lost: Simulate a timeout after Stripe succeeds. Keep FINALIZING, retrieve P1, commit SOLD once, and issue T1 once.

Worker duplicate: Send TicketRequested(O1) twice. Assert one ticket and one active token. Fail email and ensure account retrieval still works.

Gate race: Scan copies of T1 simultaneously at two gates. Assert one admission and one rejection. Revoke T1 and assert later scans fail.

Group hold: Request A-13 and an already held A-14. Assert the transaction leaves neither newly held for that order.

Operational limits and decisions

Reserved seats: This guide uses one row per numbered seat. General admission needs an atomic remaining-capacity counter and its own allocation rules.

Refund and resale: Refunding a captured payment does not automatically make a sold seat available. Before entry, revoke the old ticket, record the refund, and apply an explicit resale policy before reopening the seat. A USED ticket needs a separate post-entry refund policy and must never be resold as an unused seat.

Waiting Room: It controls how many buyers reach the app during a spike. It does not guarantee a seat, and a cached map may lag. The guarded PostgreSQL update remains the ownership rule.

Watch: claim latency, zero-row claims, hold expiry rate, FINALIZING age, Stripe status mismatches, outbox age, ticket issue retries, and duplicate gate scans. Alert on stuck states before doors open.

Key terms

Atomic claim One database operation chooses a winner.

Hold A temporary seat claim with a server deadline.

Authorization Card funds reserved for later capture.

Capture Taking the authorized payment.

Idempotency key A stable ID that makes a retry mean the same operation.

Outbox A database record of work to send after a commit.

Reconciliation Comparing external and local records to finish uncertain work.

Sources and scope

This is an example architecture, not a description of a ticket vendor's private system. The SQL and state transitions are a teaching design for numbered seats, online gates, PostgreSQL, and eligible card payments. Check provider behavior and policy before production use.
