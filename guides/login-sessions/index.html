FULL SYSTEM VIEW

The cookie points to a revocable server record

The password proves Asha once. The session identifies later requests. Each protected note still needs its own permission check.

01 / FIRST LOGIN

Asha → HTTPS login → Argon2id verify → server A memory S1 → cookie

Reloads work on A. A restart or server B cannot find S1.
02 / SHARED REQUEST PATH

Cookie S2 → server A or B → SHA-256(S2) → PostgreSQL session U1 → note permission

The server checks revocation and expiry on every protected request.
03 / LONGER AND SAFER

Idle/absolute expiry · opt-in R1 → rotate to R2 + new session · CSRF + safe rendering

A long device credential is separate from a short session. Both can be revoked.
04 / ACCOUNT CONTROL

Password reset → revoke old access · device list → revoke phone · passkey → new session

Redis can later cache reads, with PostgreSQL kept as the session authority.

Trace one request: POST /login → U1 verified → S2 cookie → GET /notes/42 → session U1 → note.owner_id=U1 IDs, durations, endpoints, and notes-app policy are a teaching design. The memory and shared-store routes replay the same hypothetical login; they do not create two real sessions for Asha.

01 / WORKING

Password and cookie

Verify an Argon2id hash, issue a random session, read it on later requests, and revoke it on logout.

02 / MULTIPLE SERVERS

Shared and bounded

Move session rows to PostgreSQL, enforce deadlines, and add a separate opt-in credential for longer device recognition.

03 / ACCOUNT CONTROL

Protect and recover

Check each resource, block forged writes, reset safely, revoke devices, and accept a passkey proof when enrolled.

Three credentials with different jobs

Password Human secret checked by Argon2id at login or password change; never used as a request cookie.

Session S2 Random short-term browser secret; hash and U1 mapping live on the server; expiry and logout end it.

Remember R1 Optional device secret with its own 30-day absolute limit; one use rotates it and creates a new session.

A passkey can replace the password proof at login. It still leads to a bounded session for later HTTP requests.
Exact HTTP exchange for the first useful login

The values S1 and S2 below stand for 32 random bytes encoded for a cookie. They are not literal production tokens. The first route stores S1 in server A memory. The grown route stores only SHA-256(S2) in PostgreSQL.

POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

email=asha%40example.test&password=...

HTTP/1.1 303 See Other
Location: /notes
Cache-Control: no-store
Set-Cookie: __Host-session=S2; Max-Age=28800; Path=/; Secure; HttpOnly; SameSite=Lax

GET /notes/42 HTTP/1.1
Cookie: __Host-session=S2

Browser: Stores and sends the cookie under its host, path, security, and age rules. Server: Hashes S2, loads an active session, gets U1, then checks note 42 belongs to U1. The password never appears in the later GET.

The __Host- prefix requires Secure, Path=/, and no Domain attribute in supporting browsers. HttpOnly is added to hide the cookie from page JavaScript. HTTPS is required for this route.

Exact session records and lookup

users: id=U1, normalized_email unique, password_hash (Argon2id encoded), email_verified_at, password_changed_at. Hash each human password with a unique salt through the library.

sessions: token_hash primary key, user_id, device_id, created_at, last_seen_at, idle_expires_at, absolute_expires_at, revoked_at. Store the SHA-256 hash of a random 256-bit token; do not store the raw cookie. A unique user ID is internal data, not a client authorization claim.

SELECT user_id, device_id
FROM sessions
WHERE token_hash = :sha256_cookie
  AND revoked_at IS NULL
  AND idle_expires_at > now()
  AND absolute_expires_at > now();
-- No row: unauthenticated. One row: check the requested object next.

For the notes route, query WHERE note_id = :note_id AND owner_id = :session_user_id. The browser-supplied URL selects a note; only the session-derived U1 can grant ownership. Extend idle expiry from server time after valid activity, never past the absolute limit.

Why two hashes differ: Argon2id slows guessing of a human password. SHA-256 is suitable here only because S2 is uniformly random and already has 256 bits of entropy.

Remember-device rotation and remote logout

remember_tokens: token_hash primary key, user_id, device_id, family_id, created_at, absolute_expires_at, consumed_at, revoked_at. R1 is a fresh random 256-bit token in a separate __Host-remember Secure, HttpOnly, SameSite=Lax cookie. Only its hash is stored.

Set-Cookie: __Host-remember=R1; Max-Age=2592000; Path=/; Secure; HttpOnly; SameSite=Lax

Refresh: The browser makes one same-origin POST /session/refresh when S2 expires. The server validates Origin, atomically consumes live R1, creates S3 and R2, and sets both cookies. It does not move the device family's 30-day absolute deadline. Coordinate browser tabs so they do not race to consume R1.

UPDATE remember_tokens
SET consumed_at = now()
WHERE token_hash = :sha256_r1
  AND consumed_at IS NULL AND revoked_at IS NULL
  AND absolute_expires_at > now()
RETURNING user_id, device_id, family_id, absolute_expires_at;
-- Require one row; insert R2 and S3 in the same transaction.

Logout here: Revoke the current session and clear its cookie. Forget this device: Revoke its session and remember family, then clear both cookies. Log out everywhere: Revoke every active session and remember family for U1. Future requests fail; a request already in flight may finish.

Rotating tokens gives an old value no right to mint more sessions. A replay can be a theft signal, but concurrent legitimate refreshes need a deliberate policy before a whole family is revoked.

Which checks protect a write?

POST /notes/42/delete: Check HTTPS; load active S2; validate the exact expected Origin; require a session-bound CSRF token in the request; verify U1 owns note 42; then delete it. Keep GET read-only. The checks apply at the server, not just in the UI.

CSRF: The browser automatically attaches cookies, so a valid S2 alone cannot show that Asha intended a cross-site request. SameSite=Lax helps but is not the only defense. The CSRF token is sent in a form field or custom header, not copied from the cookie or placed in a URL. Give each new session its own token. Login and remember-device refresh run before an active session token exists, so they use a separate same-origin policy.

XSS: Treat a note title/body as data. Escape it in HTML or use textContent; sanitize rich HTML with a maintained library. An injected same-origin script can submit actions with S2 even when HttpOnly prevents reading S2.

Sensitive changes: Require recent authentication before changing email, password, or passkey enrollment. Use the current server-side permission state near the write; a stale session cache should not grant a revoked privilege.

How a password reset closes old access

POST /password-reset-request always gives the same public answer. For U1, create a random P1, store SHA-256(P1) with a short expiry, and email a link to the verified address. Redact reset URLs from access logs and analytics.

When Asha submits a new password, use one PostgreSQL transaction to consume P1, replace U1's Argon2id hash, and revoke U1's active sessions and remember-token families. One returned row from this guarded update is the right to continue; zero means P1 was used, expired, or revoked.

UPDATE password_resets
SET used_at = now()
WHERE token_hash = :sha256_p1
  AND used_at IS NULL AND expires_at > now()
RETURNING user_id;
-- In the same transaction: update password hash, revoke sessions
-- and remember-token families for the returned user_id.

Do not create a new logged-in session from P1. Asha signs in with the new password or an existing safe passkey after the reset.

Failure drills to run before launch

Unknown email versus wrong password: Show the same public error; issue no cookie; check throttling without revealing which account exists.

Refresh and replica: Log in on server A, route the next request to B, restart A, and assert S2 still resolves from PostgreSQL. Delete the row and assert both servers deny it.

Expiry: Move server time past idle and absolute deadlines separately. Assert the browser cookie alone never restores access. A remember device may create a new session only while its own token is live.

Logout and stolen copy: Copy S2 in a test, log out, then send it again. Assert denial. Revoke a phone's remember family and assert it cannot mint a new session.

Cross-site write: Send a POST with S2 but no valid Origin or CSRF token; assert note 42 survives. Try a valid S2 against Ben's note and assert denial.

Reset token: Use P1 once, then replay it; assert the second use fails and old sessions/remember tokens remain revoked.

Passkey: Replay a challenge or change the origin; assert verification fails and no session is issued.

Cache: Revoke S2 in PostgreSQL and test cache invalidation. For a sensitive action, assert the authoritative row is checked even if Redis briefly has an old copy.

Why this guide uses server sessions

Opaque cookie: The browser carries only a random handle. PostgreSQL holds U1, expiry, device, and revocation. Logout can end a session immediately for future authoritative reads.

Signed JWT in a cookie: A server can verify a signed claim without a session lookup, but a long-lived token remains usable until expiry unless the system adds a denylist, short lifespan with refresh, or another revocation mechanism. JWT does not remove CSRF or XSS concerns when it is carried by a cookie.

Sign in with another provider: OpenID Connect adds a separate identity-provider proof and callback checks. After verifying the provider response, this notes app can still issue its own S2 and use the same request/session/authorization path. That provider flow is a separate guide-sized branch.

Key terms

Authentication Proving who is signing in.

Authorization Checking whether that user may access one resource or action.

Session ID A random browser-held handle for a server-side login record.

Bearer secret A value that grants access to whoever presents it while valid.

Idle timeout Ends a session after no activity for a chosen period.

Absolute timeout Ends a session at a fixed limit even if it stays active.

CSRF A forged browser request that uses an automatically attached credential.

XSS Untrusted page content running as script in the site's origin.

Passkey A WebAuthn credential that signs a fresh challenge with a private key kept by an authenticator.

Sources and scope

This is a teaching design for one first-party notes website on one HTTPS host. The IDs, policies, cookie ages, schema, and refresh path are examples, not a claim about a particular site's login system. Mobile apps, cross-domain single sign-on, enterprise identity, and regulated accounts need their own choices.
